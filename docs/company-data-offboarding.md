# תהליך סיום שירות ומחיקת נתוני לקוח

**גרסה:** 0.1  
**תאריך:** 2026-09-12  

> **מסמך תכנון — המחיקה הגורפת של נתוני חברה אינה מיושמת ואינה אוטומטית בשלב זה.**  
> יש לפתח route ייעודי לפני שניתן לבצע offboarding באופן מסודר וניתן לביקורת.

---

## 1. מטרה

הגדרת תהליך מסודר, מתועד, ועמיד לביקורת לסיום חוזה עם לקוח ומחיקת כלל נתוניו מהמערכת. תהליך זה נדרש לצורך:

- עמידה בחובות מדיניות הפרטיות ("זכות למחיקה / שכחה" בהתחשב בדין החל).
- עמידה בהתחייבויות ה-DPA מול לקוחות.
- ניקיון ותחזוקה תפעולית של בסיס הנתונים.

---

## 2. שלבים מומלצים

### א. השבתת גישה
- הגדר `companies.is_active = false` דרך ממשק מנהל הפלטפורמה.
- פעולה זו **כבר קיימת** ומשביתה מיידית את גישת כל חברי החברה.
- המשתמשים רואים הודעת "החברה אינה פעילה" ואינם יכולים לגשת לנתונים.

### ב. ייצוא נתונים
- הפק ZIP export מלא של נתוני החברה לאחסון חיצוני (כגיבוי לצורך ביקורת או לספק ללקוח).
- ה-ZIP export **כבר קיים** במערכת (Admin UI).
- יש לשמור את הייצוא בהתאם למדיניות השמירה הפנימית `[LEGAL REVIEW REQUIRED]`.

### ג. תקופת חסד
- **30 יום** מתאריך סיום החוזה — מומלץ לשמר את הנתונים לפני מחיקה סופית.
- במהלך תקופה זו, החברה מושבתת (is_active = false) אך הנתונים לא נמחקים.
- לקוח יכול לפנות לבקשת ייצוא נתונים אחרון בתקופה זו.

### ד. הודעה ללקוח
- שלח הודעה ללקוח לפני מחיקת הנתונים (לפחות 7 ימי עסקים מראש), עם אפשרות לבקש ייצוא נוסף.
- תעד שהודעה נשלחה (תאריך, נמען, אמצעי).

### ה. מחיקת נתונים
- ביצוע על-ידי מנהל הפלטפורמה בלבד דרך ה-route הייעודי (ראה סעיף 8).
- כל הפעולות מתועדות ב-audit_log.

## 4. Storage (Supabase Bucket: `worker-files`)

יש למחוק את כל הקבצים הבאים:

| נתיב ב-Bucket | תיאור |
|--------------|-------|
| `{company_id}/workers/{worker_id}/` | תמונות עובדים, מסמכי זהות, רישיונות |
| `company-logos/{company_id}/` | לוגו החברה |
| `briefings/{worker_id}/` | קובצי תדריכי בטיחות (מיפוי דרך workers → company_id) |
| `signatures/{worker_id}/` | חתימות עובדים ומנהלים (מיפוי דרך workers → company_id) |

> **שים לב:** נתיבי `briefings/` ו-`signatures/` ממופים לפי `worker_id`, לא `company_id`. יש לאחזר רשימת worker_ids של החברה לפני מחיקת קבצי Storage, או לבצע מחיקה לאחר מחיקת רשומות ה-`workers` על סמך הרשימה שנשמרה.
>
> **כרגע אין מיפוי ישיר company_id → כל נתיבי Storage לכל סוגי הקבצים.** נדרשת בדיקה נוספת להבטחת כיסוי מלא.

## 5. פרופיל משתמש (`profiles`)

| מצב | פעולה מומלצת |
|-----|-------------|
| המשתמש שייך לחברה אחת בלבד (החברה המוסרת) | בטל פעילות הפרופיל (`is_active = false`); שמור רשומה לצורך audit |
| המשתמש שייך לחברות נוספות | **אל תמחק / אל תשנה** את הפרופיל; הסר רק את ה-`company_members` record |
| חשבון Supabase Auth | `[LEGAL REVIEW REQUIRED]` — מחיקת auth user מחייבת בדיקה האם המשתמש פעיל בחברות אחרות |

## 6. מדיניות שמירה לאחר מחיקה

**`[LEGAL REVIEW REQUIRED]`**

קיימות חובות שמירה שעלולות לסתור מחיקה מיידית:

- **רשומות בטיחות ותאונות עבודה** — חוק הבטיחות בעבודה עשוי לחייב שמירה לתקופה מסוימת לאחר סיום ההעסקה.
- **מסמכי זהות (תעודות זהות)** — שמירת עותק של ת.ז. עשויה להיות כפופה להגבלות.
- **הערכות עובדים** — תקופת שמירה לצורכי תביעות עבודה.
- **`audit_logs` ו-`legal_acceptances`** — ראיות על פעולות מנהליות ועל הסכמת משתמש.

קבל חוות דעת משפטית לגבי כל קטגוריה לפני הגדרת מדיניות מחיקה סופית.

## 7. תיעוד מחיקה

לכל פעולת offboarding יש לרשום ב-`audit_logs` (הפנימי של SafeDoc) ובמסמך נפרד:

| שדה | ערך |
|-----|-----|
| `company_id` | מזהה החברה שנמחקה |
| `company_name` | שם החברה (לפני מחיקה) |
| `deleted_by` | user_id של מנהל הפלטפורמה שביצע |
| `deleted_at` | timestamp |
| `export_performed` | האם בוצע ZIP export לפני מחיקה (true/false) |
| `tables_deleted` | רשימת הטבלאות שנמחקו |
| `storage_paths_deleted` | רשימת נתיבי Storage שנמחקו |
| `records_count` | מספר רשומות שנמחקו לפי טבלה |
